# 대립형 코드 리뷰 서비스 — 계획 문서

원본 설계 문서(브레인스토밍 산출물): `docs/superpowers/specs/2026-09-07-adversarial-code-review-design.md` (수정하지 않고 그대로 보존)
API request/response 상세 스키마: `openapi.yaml` 참조(이 문서에는 포함하지 않음). 사람이 읽는 요약은 `docs/api.md` 참조
개발 일정·작업 순서: `docs/plans/develop_plan.md` 참조(이 문서에는 포함하지 않음)

## 1. 문제 정의

LLM 기반 코드 리뷰는 흔히 두 가지 문제를 가진다.

1. 지적한 문제의 근거(코드 위치)가 불명확해, 사용자가 리뷰어가 실제로 그 부분을 읽고 판단했는지 검증할 방법이 없다.
2. 하나의 모델이 일방적으로 판단을 내리기 때문에, 편향되거나 근거가 빈약한 지적도 반박 없이 그대로 받아들여진다.

이 서비스는 검사(기소)·변호인(반박)·판사(판결) 3역할의 대립 구조로 리뷰 과정을 나누고, 모든 지적에 실제 코드 라인 증거를 강제해 서버가 대조 검증하며, 판정 결과를 JSON 스키마로 고정해 사후 검증과 판례 축적이 가능하게 한다. 목표는 "더 똑똑한 리뷰어"가 아니라 **검증 가능하고 재현 가능한 리뷰 프로세스**를 만드는 것이다.

## 2. 목표 / 비목표

### 목표

- 사용자가 코드를 붙여넣으면(또는 GitHub 링크로 지정하면) 검사(기소) → 변호인(반박) → 판사(판결+형량) 3단계를 순차 실행하는 대립형 코드 리뷰 서비스를 만든다.
- 기소는 사전 정의된 법전(rule catalog)의 rule_id로만 가능하고, 모든 기소는 코드 라인 범위 증거를 지목하며 서버가 실제 라인 수와 대조해 검증한다.
- 각 단계 출력은 JSON 스키마로 강제하고 서버가 검증하며, 실패 시 재시도 상한을 둔다.
- 형량은 실행 가능한 리팩토링 과제 체크리스트로 산출되고, 완료 여부를 서버에 저장할 수 있다.
- 사용자는 확정 판결에 대해 1회 항소할 수 있고, 재심은 판사 단계만 재실행한다.
- 과거 판결은 판례로 축적되어 이후 판결에 참고된다.

### 비목표

- 코드 실행/테스트
- 자동 PR 생성
- 레포지토리 전체 분석(다중 파일, 파일 간 의존성 분석)은 비목표다. GitHub 링크 제출은 저장소 내 단일 파일을 지정하는 방식이며, 여전히 한 번에 한 파일만 심사한다. 링크 제출과 레포 전체 분석은 다른 것이다.
- 실시간 협업
- 기소 단위 부분 항소(v1은 사건 전체 재심만)
- 소셜 로그인, 이메일 인증 메일 발송
- 비밀번호 재설정/계정 복구 — 이메일 발송이 비목표이므로 링크 기반 재설정도 함께 제외한다. 보안 질문 방식은 답변이 추측·조사로 획득 가능해 비밀번호보다 약한 인증 수단이 되므로 대안으로 채택하지 않는다. 이메일 발송이 가능해지는 시점에 링크 기반 재설정으로 구현한다.
- 비공개(private) GitHub 저장소 지원 — OAuth 범위 확대를 피하기 위해 public 저장소만 지원한다.
- 법전 관리자 CRUD UI(법전은 배포 시 파일 수정으로 관리)

## 3. 설계 결정과 근거

브레인스토밍 과정에서 결정된 항목 중, 이유가 코드나 스키마만 봐서는 드러나지 않는 것들을 정리한다.

| 결정                                                                                                                         | 근거                                                                                                                                                                                                                                                                                                                                               |
| ---------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 검사/변호인/판사/재심 전 역할에 단일 LLM 모델 + 역할별 프롬프트 사용                                                         | 비용 예측이 쉽고 구현이 단순함. 학교 과제 규모에서 모델 간 정합성 관리 오버헤드가 얻는 이득보다 큼                                                                                                                                                                                                                                                 |
| 별도 브로커(Redis/Celery) 없이 PostgreSQL 폴링 큐, 워커는 "사건" 단위가 아니라 "스테이지" 단위로 작업                        | 3단계를 한 트랜잭션으로 묶으면 수십 초 락이 걸리고, 중간에 워커가 죽으면 어디까지 됐는지 알 수 없음. 스테이지 단위 커밋이면 재개 지점이 `status` 값만으로 결정됨                                                                                                                                                                                   |
| 워커 하트비트(LLM 호출 전후 `locked_at` 갱신) + 조건부 완료 커밋, 타임아웃 15분                                              | `locked_at`만으로 크래시를 판단하면 "느리지만 살아있는" 워커와 "죽은" 워커를 구분 못해 같은 스테이지가 이중 처리될 수 있음. 완료 커밋을 조건부 UPDATE로 만들면 늦게 도착한 쪽은 0행 적용되어 조용히 버려짐(이중 커밋 방지). 5분은 정상 처리 중에도 재수거가 발생할 만큼 짧았음                                                                     |
| 검사 출력엔 `charge_index`가 없고, 서버가 폐기 검증 후 0부터 연속 재부여                                                     | 검사가 직접 인덱스를 매기면 폐기된 기소만큼 구멍이 생겨 이후 단계(변호/판사)의 참조가 깨짐                                                                                                                                                                                                                                                         |
| severity(심각도)와 effort(수정 비용)를 독립된 축으로 분리                                                                    | 감형이 곧 "고치기 쉬워짐"을 의미하지 않음 — HIGH 취약점이 한 줄 수정일 수 있고 LOW 네이밍이 40곳 수정일 수 있음. effort는 법전의 `typical_effort`를 기준으로 판례 주입을 통해 수렴시킨다                                                                                                                                                           |
| severity 범위(±1) 초과는 charge 완전 폐기, effort 범위 초과는 경계값 클램프(비대칭 처리)                                     | severity 오류는 죄목을 잘못 고른 것과 구별이 안 되고 폐기해도 다른 기소가 남지만, sentence를 폐기하면 채택된 죄목에 형량이 없는 판결문이 되어 결과가 불완전해짐                                                                                                                                                                                    |
| `revision`(판결 내용 버전)과 `appeal_used`(항소 소진 여부)를 별도 필드로 분리                                                | 재심이 실패해도 항소 기회는 소진되어야 하는데, 한 필드로 "버전"과 "소진 여부"를 동시에 표현하면 재심 실패 시 두 의미가 충돌함(재항소를 막으려면 소진 표시가 필요하지만, 판결 내용은 원심 그대로 유지해야 함)                                                                                                                                       |
| 유효 기소 0건이면 변호/판사 스테이지를 건너뛰고 즉시 `DISMISSED`로 종결(별도 종료 상태)                                      | 판단할 기소 자체가 없으므로 변호·판사 LLM 호출 두 번을 아낄 수 있음                                                                                                                                                                                                                                                                                |
| 판례 조회는 벡터/키워드 검색이 아니라 `(rule_id, language)` 구조화 조회                                                      | `rule_id`가 이미 "동일한 죄목"을 정확히 식별하는 정규화된 키. 임베딩 검색은 다른 조항의 판례를 유사하다고 끌어올 위험이 있어 판결 일관성에 오히려 역효과                                                                                                                                                                                           |
| 항소로 뒤집힌 원심 판례는 조회에서 제외하되 데이터는 삭제하지 않음(`is_overturned` 플래그)                                   | 삭제하면 통계·분석에 못 쓰게 됨. 재심이 실패하면 애초에 뒤집을 새 판결이 없으므로 원심은 그대로 유효                                                                                                                                                                                                                                               |
| 코드 해시 캐시 키는 `(user_id, code_hash, language)`뿐 — GitHub 출처(`repo_url`/`commit_sha`/`file_path`)는 캐시 키에서 제외 | 캐시의 목적은 "동일 코드에 LLM을 중복 지출하지 않는 것"이므로 출처가 달라도 내용이 같으면 재사용하는 게 맞음(포크 저장소, 붙여넣기 후 링크 재제출이 실제로 흔함). 단 캐시 히트 응답에 원 사건의 출처를 항상 노출해 혼란을 막음                                                                                                                     |
| 진행 중 사건 중복 생성 방지를 애플리케이션 로직이 아니라 DB 부분 유니크 인덱스로 구현                                        | "조회 후 삽입" 방식은 동시 요청 두 개가 동시에 통과할 수 있는 레이스 컨디션이 있어 실질적 방어가 안 됨                                                                                                                                                                                                                                             |
| 일일 제출 제한을 자정 리셋이 아니라 24시간 슬라이딩 윈도우로 구현                                                            | 자정 리셋은 리셋 직후 사실상 한도가 두 배가 되는 허점(23:50에 20건, 00:00에 다시 20건)이 있음                                                                                                                                                                                                                                                      |
| 사건당 기소 건수 상한(12건), severity 높은 순으로 절단                                                                       | 상한이 없으면 검사가 수십 건을 기소하는 사건이 생겨 판사 프롬프트가 부풀고, verdict 누락과 재시도 비용이 함께 폭증함. 사후 지표(`verdict_missing_rate`)만으로는 예방이 안 됨                                                                                                                                                                       |
| JWT를 httpOnly + Secure 쿠키로 저장(localStorage 미사용). SameSite는 로컬/개발은 Lax, 운영(`ENVIRONMENT=production`)은 None  | XSS로 세션이 탈취될 경우의 파급 범위를 고려해 JS 접근 가능한 저장소를 배제. 운영은 프론트/백엔드가 서로 다른 도메인(Render 서비스 두 개)이라 SameSite=Lax면 크로스 사이트 요청에 쿠키가 실리지 않아 None+Secure로 완화 — CSRF 방어는 SameSite가 아니라 커스텀 헤더(`X-CSRF-Protection`, 아래 행)가 맡고 있어 이 완화가 CSRF 보호를 약화시키지 않음 |
| CSRF 대응은 Double Submit Cookie 대신 커스텀 헤더(`X-CSRF-Protection`) 검증을 채택                                           | 프론트엔드 출처로 CORS를 제한하는 한 단순 폼 제출은 커스텀 헤더를 실어 보낼 수 없고 fetch/XHR는 preflight에서 막히므로 동일한 방어 효과를 별도 토큰 쿠키 발급·비교 로직 없이 얻을 수 있음                                                                                                                                                          |
| GitHub 링크 제출 시 브랜치명이 아니라 커밋 SHA를 고정 저장                                                                   | 브랜치명만 저장하면 저장소가 재판 도중·이후 바뀌었을 때 증거 라인 검증의 기준 자체가 흔들림                                                                                                                                                                                                                                                        |
| GitHub fetch 실패는 일일 제출(사건 생성) 카운트에서 제외하되, fetch 시도 자체에 별도 rate limit(24시간 60회)을 둠            | fetch 실패는 LLM 비용이 없어 카운트에서 빼는 게 맞지만, 그대로 두면 서버가 사용자 대신 GitHub API를 무제한 대행 호출하는 구멍이 생김                                                                                                                                                                                                               |
| 스테이지 재시도 상한을 `stage_attempts ≤ 3`(총 시도 횟수)으로 고정, LLM provider의 429는 이 카운터에서 완전히 제외           | 재시도 시 실패 사유를 프롬프트에 포함하므로 2회 안에 안 고쳐지면 구조적 문제일 가능성이 높아 더 늘려도 성공률이 안 오름. 429는 출력 품질과 무관한 provider 제약이라 같은 카운터에 넣으면 사용자가 잘못 없이 사건을 잃고 일일 카운트까지 소모하게 됨                                                                                                |

## 4. 사건 상태머신

`status` 컬럼 하나로 "다음에 할 일"과 "지금 진행 중인 일"을 함께 표현한다(`QUEUED_*` = 픽업 대기, 동사형 = 워커가 잠금 보유 중).

| 상태                 | 의미                                                                      | 잠금 컬럼            |
| -------------------- | ------------------------------------------------------------------------- | -------------------- |
| `QUEUED_PROSECUTION` | 제출 직후, 검사 대기                                                      | -                    |
| `PROSECUTING`        | 워커가 검사 단계 처리 중                                                  | locked_at, locked_by |
| `QUEUED_DEFENSE`     | 검사 완료, 변호인 대기                                                    | -                    |
| `DEFENDING`          | 워커가 변호 단계 처리 중                                                  | locked_at, locked_by |
| `QUEUED_JUDGMENT`    | 변호 완료, 판사 대기                                                      | -                    |
| `JUDGING`            | 워커가 판결 처리 중                                                       | locked_at, locked_by |
| `SENTENCED`          | 판결 확정 (revision 0 또는 1)                                             | -                    |
| `DISMISSED`          | 검사 유효 기소 0건으로 무혐의 종결(변호/판사 스테이지 자체를 거치지 않음) | -                    |
| `QUEUED_REJUDGMENT`  | 항소 접수, 재심 대기                                                      | -                    |
| `REJUDGING`          | 워커가 재심(판사만) 처리 중                                               | locked_at, locked_by |
| `FAILED`             | 재시도 상한 초과로 종결                                                   | -                    |

`DISMISSED`는 `SENTENCED`와 별개의 종료 상태다. 판결(`judgments`) 자체가 존재하지 않으므로 항소 대상이 아니고, 판례로도 적재되지 않는다.

### 전이표

| From                                | 트리거                                           | To                                          | 비고                                                                                                               |
| ----------------------------------- | ------------------------------------------------ | ------------------------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| QUEUED_PROSECUTION                  | 워커 폴링 픽업                                   | PROSECUTING                                 | `SELECT ... FOR UPDATE SKIP LOCKED`, locked_at/locked_by 기록                                                      |
| PROSECUTING                         | 검증 통과, 살아남은 charge 0건                   | **DISMISSED**                               | 변호/판사 스테이지를 거치지 않고 즉시 종결                                                                         |
| PROSECUTING                         | 검증 통과, 살아남은 charge 1건 이상              | QUEUED_DEFENSE                              |                                                                                                                    |
| PROSECUTING                         | 검증 실패, `prosecution_attempts` < 3            | QUEUED_PROSECUTION                          | `prosecution_attempts`+1(재시도 프롬프트에 실패 사유 포함)                                                         |
| PROSECUTING                         | `prosecution_attempts` == 3                      | FAILED                                      | `failed_stage=PROSECUTION`                                                                                         |
| PROSECUTING                         | `locked_at` 15분 초과(워커 크래시)               | QUEUED_PROSECUTION                          | 다른 워커가 재수거, `prosecution_attempts`는 유지, 완료된 스테이지는 재실행하지 않음                               |
| QUEUED_DEFENSE                      | 워커 픽업                                        | DEFENDING                                   |                                                                                                                    |
| DEFENDING                           | 검증 통과 / 실패·재시도 / `defense_attempts`==3  | QUEUED_JUDGMENT / QUEUED_DEFENSE / FAILED   | 위와 동일 패턴                                                                                                     |
| QUEUED_JUDGMENT                     | 워커 픽업                                        | JUDGING                                     |                                                                                                                    |
| JUDGING                             | 검증 통과 / 실패·재시도 / `judgment_attempts`==3 | SENTENCED(rev=0) / QUEUED_JUDGMENT / FAILED | 위와 동일 패턴                                                                                                     |
| SENTENCED(rev=0, appeal_used=false) | 사용자 항소 (rebuttal≥20자)                      | QUEUED_REJUDGMENT                           | `appeal_used=true` 즉시 확정(성공/실패 무관, 소진)                                                                 |
| SENTENCED(appeal_used=true)         | 재항소 시도                                      | -                                           | `409`(전이 없음)                                                                                                   |
| QUEUED_REJUDGMENT                   | 워커 픽업                                        | REJUDGING                                   | 검사/변호 결과는 재사용, 판례만 새로 조회                                                                          |
| REJUDGING                           | 검증 통과                                        | SENTENCED(revision=1)                       | 원심(rev=0) `judgments.is_overturned=true` 전환, 신규 판례로 revision=1 적재                                       |
| REJUDGING                           | 실패·재시도, `rejudgment_attempts` < 3           | QUEUED_REJUDGMENT                           | `rejudgment_attempts`+1(재시도 프롬프트에 실패 사유 포함)                                                          |
| REJUDGING                           | `rejudgment_attempts` == 3                       | **SENTENCED(revision=0 유지)**              | `rejudgment_failed_reason`/`rejudgment_failed_at` 기록, 원심 유효 유지, 항소 기회는 이미 소진, 판례/캐시 대상 아님 |
| FAILED                              | (전이 없음, 종결)                                | -                                           | 사용자는 재제출(새 사건 생성)                                                                                      |

### 스테이지 시도 횟수(`stage_attempts`) 정의

`prosecution_attempts`/`defense_attempts`/`judgment_attempts`/`rejudgment_attempts`는 **"재시도 횟수"가 아니라 "총 시도 횟수"**다. 상한은 **`stage_attempts ≤ 3`**(최초 시도 1회 + 재시도 2회 = 스테이지당 LLM 호출 최대 3회)이며, "재시도 2회"와 "총 3회"를 혼용하지 않는다.

- **근거**: 재시도 시 직전 실패 사유(스키마 오류, 누락된 `charge_index` 등)를 프롬프트에 포함하므로, 2회 안에 교정되지 않는 실패는 일시적 오류가 아니라 프롬프트·스키마의 구조적 문제일 가능성이 높다. 상한을 더 늘려도 성공률은 오르지 않고 비용과 지연만 증가한다.
- **지연 예산과의 연결**(§11): 사건당 목표 지연이 90초인데 스테이지당 최대 3회 호출이 허용되면, 최악의 경우 4단계(검사/변호/판사/재심) × 3회 = 12회 호출로 예산을 크게 초과한다. 따라서 재시도는 **예외적 경로**로 취급하고, `verdict_missing_rate` 등 지표가 높게 나오면 재시도 상한 자체를 늘리는 대신 프롬프트를 보강하거나 기소 건수 상한(12건)을 낮추는 쪽으로 대응한다.
- **429(rate limit)는 `stage_attempts`에서 제외**한다. LLM provider의 429 응답은 출력 품질 문제가 아니라 provider 측 제약이므로, `stage_attempts`와 완전히 분리된 카운터로 지수 백오프(exponential backoff) 재시도한다. 이렇게 분리하지 않으면 사용자가 아무 잘못 없이 사건을 잃고(`FAILED`) 일일 제출 카운트까지 소모하게 되어 부당하다.

### 화면 표시 매핑 (`revision` × `appeal_used`)

| revision | appeal_used | 표시                  |
| -------- | ----------- | --------------------- |
| 0        | false       | 판결 확정 (항소 가능) |
| 0        | true        | 원심 확정 (재심 실패) |
| 1        | true        | 재심 확정 (최종)      |

## 5. 단계별 JSON 스키마와 서버 검증 규칙

### 5.1 검사(Prosecution) 출력

```json
{
  "charges": [
    {
      "rule_id": "SEC-003",
      "evidence_lines": [42, 58],
      "charged_severity": "HIGH",
      "severity_adjusted": true,
      "severity_reason": "사용자 입력이 검증 없이 쿼리에 직접 들어감",
      "description": "..."
    }
  ]
}
```

`charge_index`는 출력에 없다. 서버가 검증 후 부여한다. 처리 순서(각 charge 단위):

1. `rule_id`가 활성 법전에 존재하고 `language` 일치(또는 언어무관 공통 조항) → 아니면 charge 완전 폐기
2. `evidence_lines`가 `[1, 실제라인수]` 범위 내, start ≤ end → 아니면 charge 완전 폐기
3. `charged_severity`가 `default_severity` ±1단계를 벗어남 → charge 완전 폐기
4. `severity_adjusted=true`인데 `severity_reason`이 없거나 부실(10자 미만) → charge는 유지, 조정만 무효화(`severity_adjusted=false`, `charged_severity=default_severity`로 리셋)
5. 사건당 기소 건수 상한(12건): 1~4단계를 통과한 charge가 12건 초과면 `charged_severity` 높은 순으로 상위 12건만 채택, 나머지 폐기(`cases.charges_truncated=true` 기록)
6. 살아남은 charge에 `charge_index`를 0부터 연속 재부여(원본 순서는 내부 `raw_index`로만 보관)
7. JSON 형태 자체가 스키마를 안 갖춘 경우에만 스테이지 재시도
8. 살아남은 charge가 0건이면 즉시 `DISMISSED`로 종결

### 5.2 변호인(Defense) 출력

```json
{ "pleas": [{ "charge_index": 0, "plea": "DENY", "argument": "..." }] }
```

- `plea` ∈ `ADMIT / DENY / NO_RESPONSE`
- 존재하지 않는 `charge_index` 참조 → 폐기 / 중복 참조 → 첫 항목만 인정
- 응답에 없는 `charge_index` → 서버가 `plea=NO_RESPONSE, argument=""`로 자동 채움
- 채운 뒤 모든 charge가 NO_RESPONSE면 대립 구조 붕괴로 간주, 스테이지 재시도

### 5.3 판사(Judgment, 재심 공통) 출력

```json
{
  "opinion": "총평...",
  "verdicts": [
    {
      "charge_index": 0,
      "verdict": "REDUCED",
      "final_severity": "MEDIUM",
      "reasoning": "..."
    }
  ],
  "sentences": [
    {
      "charge_index": 0,
      "task": "...",
      "target_lines": [42, 60],
      "effort": "MEDIUM",
      "effort_adjusted": true,
      "effort_reason": "호출부 40곳에 영향",
      "effort_clamped": false,
      "advisory": false,
      "rationale": "..."
    }
  ],
  "rebuttal_accepted": true
}
```

`rebuttal_accepted`는 재심에서만 필수. 검증 규칙:

- `charge_index`가 유효한 재부여 인덱스를 가리켜야 함, 중복이면 첫 항목만 인정
- `final_severity ≤ charged_severity`(상승 불가). `REDUCED`는 `charged_severity ∈ {HIGH, MEDIUM}`이면 정확히 1단계 하락, `LOW`면 `LOW` 유지 + `advisory=true`
- `sentences`는 `SUSTAINED`/`REDUCED` charge에만 존재. sentence 폐기는 `charge_index`/`target_lines` 검증 실패 때만
- severity와 effort는 독립 — 감형은 severity 1단계 하락만 의미, effort는 변경되지 않음
- `effort`는 `typical_effort` ±1이 기본 허용 범위. `effort_reason` 부실 시 조정 무효화(리셋), 사유가 충실해도 범위 초과 시 경계값으로 클램프(`effort_clamped=true`) — sentence는 폐기하지 않음
- 재심에서 `rebuttal_accepted` 누락 → 스테이지 재시도
- 살아있는 charge 중 일부에 `verdict`가 통째로 빠짐 → 불완전한 판결로 간주해 스테이지 재시도(서버가 누락분을 대신 채우지 않음, 재시도 프롬프트에 누락된 인덱스를 구체적으로 명시), 상한 소진 시 일반 스키마 실패와 동일 처리

### 5.4 재심 판사 입력

코드 + 확정 기소장 + 변호인 반박 + 신규 판례 조회 결과 + `appeal.rebuttal`(사용자 항소 사유, 필수). 검사/변호 단계는 재실행하지 않고 재사용한다. 프롬프트 지침: "사용자 반박은 주장일 뿐 그 자체가 근거는 아니다. 코드와 조항에 비추어 판단하고, 반박을 수용/기각한 이유를 `reasoning`에 남겨라."

### 5.5 스키마 검증 재시도 상한 초과 시(FAILED)

- 완료된 스테이지의 산출물은 보존되어 열람 가능
- `failed_stage`, `failure_reason`을 사건에 기록
- FAILED 사건은 판례로 적재하지 않고, 코드 해시 캐시 대상에서도 제외
- 화면에는 "다시 제출" 버튼만 제공(자동 재시도 없음)

## 6. 법전 작성 기준

포함 기준 — 아래 셋을 모두 만족하는 조항만 법전에 넣는다.

1. **라인 지목 가능성**: 위반 위치를 코드 라인으로 특정할 수 있어야 한다. 특정할 수 없으면 증거 라인 검증이 작동하지 않아 환각 차단 장치가 무력해진다. 기소 형식이 라인 범위를 요구하므로 지목할 수 없는 지적은 애초에 표현되지 않는다. 즉 판정 가능성은 주관적 판단이 아니라 출력 형식이 강제하는 요건이다.
2. **판정 객관성**: 프로젝트 규약에 따라 옳고 그름이 갈리지 않아야 한다.
3. **실행 불필요**: 코드를 실행하지 않고 정적으로 판정 가능해야 한다.

제외 기준과 실제 탈락 예시:

| 후보 조항                    | 탈락 사유                                       |
| ---------------------------- | ----------------------------------------------- |
| "설계에 확장성이 없다"       | 라인 지목 불가                                  |
| "들여쓰기가 일관되지 않다"   | 포매터가 자동 처리, 사람의 판단 가치 없음       |
| "이 반복문이 느리다"         | 실측 없이 근거 불가                             |
| "주석이 부족하다"            | 팀 규약에 따라 갈림                             |
| "파일 구조가 관례에 안 맞다" | 단일 파일만 다루므로 판정 불가                  |
| "테스트가 없다"              | 제출 대상 파일 밖의 사실이라 지목할 라인이 없음 |

카테고리 6개와 각각이 보는 대상:

- **SECURITY**: 외부 입력을 신뢰하는 지점
- **ERROR**: 실패를 처리·은폐하는 방식
- **STRUCTURE**: 책임 분리·길이·중첩
- **NAMING**: 식별자가 의미를 드러내는가
- **PERF**: 정적으로 확인 가능한 비효율
- **STYLE**: 가독성

언어 종속 여부의 기준: 특정 언어의 문법이나 API를 알아야 판정되는 조항만 `languages`를 지정하고, 함수 길이·중첩 깊이처럼 세기만 하면 되는 것은 공통 조항(`languages: []`)으로 둔다. "기타" 언어 제출 시에도 심사가 성립할 최소 조항 수를 확보하기 위해 공통 조항을 과반으로 유지한다.

조항 근거 표기: 보안·예외 처리·복잡도 관련해 널리 통용되는 코딩 관행에서 도출했다고 서술하고, 특정 표준의 조항 번호는 인용하지 않는다. 확인하지 않은 표준을 인용하면 검증 불가한 주장이 되기 때문이며, 조항 선정의 실제 기준은 표준 준수가 아니라 위 포함 기준 3개다.

조항 타당성의 사후 검증: 조항 자체가 타당한지는 기각률 지표(§11)로 사후 검증한다. 특정 조항의 기각률이 지속적으로 높으면 과잉 조항(검사가 기소하지만 판사가 계속 기각하는 조항)으로 보고 `active: false`로 내린다.

실제 조항 전체 목록(현재 20개, 공통 14 / 언어종속 6)은 `rules.yaml`에 있다.

## 7. 판례 조회 방식

판사는 자유 키워드로 검색하지 않는다. 구조화된 조회를 수행한다.

- 조회 키: `(rule_id, language)`
- 필터: `is_overturned = false AND status = 'SENTENCED' AND case_id != 현재 사건`
- 정렬: 동일 `language` 우선 → `created_at` 최신순
- 상한: 기소당 3건, 사건 전체 10건 (severity 높은 기소부터 채운다)

키워드·임베딩 검색을 쓰지 않는 근거: `rule_id`가 이미 "동일한 죄목"을 정확히 식별하는 정규화된 키다. 판사가 알아야 하는 것은 "이 조항이 과거에 어떻게 판정됐는가"이며, 이는 텍스트 유사도가 아니라 조항 일치로 정확히 조회된다. 임베딩 검색은 조항이 다른 판례를 유사하다고 끌어올 위험이 있어 판결 일관성에 오히려 역효과다.

주입된 판례는 `precedent_verdict_ids`로 기록되어, 어떤 판례를 보고 내린 판결인지 사후 추적이 가능하다.

판례 적재 기준(보강): 항소로 뒤집힌 원심 판결은 조회에서 제외하되 데이터는 보존한다(`is_overturned` 플래그, 통계용으로는 사용 가능). 이 전환은 재심이 실제로 성공했을 때만 일어나며, 재심 실패 시 원심은 그대로 유효하다. `FAILED`/`DISMISSED` 사건은 애초에 판결(`judgments`)이 없어 조회에 걸리지 않는다.

1. 로그인 / 회원가입 (비밀번호 찾기 링크 없음 — 비목표)
2. 코드 제출 — 붙여넣기/GitHub 링크 두 입력 모드, 언어 선택(고정 목록, 링크 모드는 확장자 추론 후 확인/변경 가능), 캐시 히트 시 출처 표시 + 재판 강행 옵션, "기타" 선택 시 공통 조항 수 안내
3. 사건 진행 — 2초 폴링, 스테이지 표시, FAILED 시 재제출 버튼
4. 판결문 — 기소장 + 변론 + 판결 + 형량 체크리스트(완료 토글) + 항소 버튼, GitHub 링크 제출이면 저장소/커밋/경로 표시
5. 항소 입력 모달
6. 재심 결과 — 최종 판결 또는 "재심 실패, 원심 유지" 배너
7. 마이페이지 / 전과 기록 — 사건 목록, rule_id별 반복 통계
8. 법전 열람

## 10. 엣지 케이스

**입력 검증**: 비코드 텍스트 경고, 시크릿 마스킹 경고, 미지원 언어→기타 접수, 크기 초과 400, 일일 한도 429

**검사/변호/판사**: 기소 0건→DISMISSED, 반박 전무→재시도, severity/effort 조정 부실→리셋, effort 범위초과→클램프, 기소 12건 초과→severity순 절단, verdict 누락→재시도(누락 인덱스 명시), 판례 상한초과→severity순 절단, 판례 없음→정직하게 전달

**동시성/장애**: 워커 크래시(15분 타임아웃 재픽업, 완료 스테이지 재실행 안 함), 느린 워커의 조건부 커밋 실패(0행 적용, `stale_commit_rate`로 관찰), 재시도 상한 초과→FAILED

**항소/재심**: 재심 실패해도 원심 유효 유지 + 항소 소진, `revision=1`에 재항소 시도→409, 재심 성공 시 원심만 overturned 처리

**법전/캐시**: 조항 비활성화 후에도 과거 판결 조회 가능, 사소한 수정으로 해시 우회는 `force_retrial`로 대응, 동일 코드 연속 제출은 DB 유니크 인덱스로 진행중 사건 재사용, DISMISSED도 캐시 대상(단 판례 적재는 안 됨)

**GitHub 링크**: 디렉터리 링크→400, private/404→400, GitHub API 오류/rate limit→503, fetch 자체는 별도 rate limit(24시간 60회)

**접근 제어**: 남의 `case_id`/`sentence_id` 조회 시도 → 404(403 아님)

## 11. 비용·지연 예산

- **LLM 호출 횟수**: 정상 경로(재시도 없음) 기준 사건당 3회(검사/변호/판사 각 1회, `stage_attempts=1`). 항소 시 재심 1회(판사만) 추가. 스테이지당 **총 시도 횟수는 최대 3회**(`stage_attempts ≤ 3`, §4)로 상한을 둔다 — 최초 1회 + 재시도 2회. 사건당 목표 지연 90초에 스테이지당 최대 3회 호출이 겹치면 최악의 경우 4단계 × 3회 = 12회 호출로 예산을 크게 초과하므로, 재시도는 예외적 경로로 취급하고 `verdict_missing_rate` 등이 높으면 상한을 늘리지 않고 프롬프트나 기소 상한(12건)을 조정한다(§4).
- **지연**: LLM 호출은 각 수십 초. `stage_attempts=1`(정상 경로) 기준 검사→변호→판사 합산 약 1~2분 + 2초 폴링 오버헤드. 재시도 발생 시 스테이지당 최대 3배까지 늘어난다. 429(rate limit)로 인한 지수 백오프 대기는 `stage_attempts`와 별도 카운터라 이 지연 예산 계산에 포함되지 않는다(§4) — provider 제약이라 사용자 귀책이 아니므로 별도로 다룬다.
- **프롬프트 크기 상한**: 판례는 사건당 최대 10건·기소당 최대 3건, 기소는 사건당 최대 12건으로 상한을 둬 판사 프롬프트 토큰 사용량을 예측 가능한 범위로 제한.
- **외부 비용**: GitHub API는 자격증명 없는 public 호출(무료), rate limit은 fetch 시도 제한(60회/24h)으로 서버가 대신 소모.
- **스토리지**: 코드 스냅샷(최대 20000자)을 사건마다 영구 저장 — 사용자당 일일 20건 제출 제한이 사실상 스토리지 증가 속도의 상한 역할도 겸한다.

### LLM 호출 절약 장치

정상 경로 3회(검사·변호·판사 각 1회)를 기준으로, 아래 네 장치가 각각 몇 회를 절약하는지 명시한다.

| 장치                                         | 절약량 | 무엇을 아끼는가                                                                             |
| -------------------------------------------- | ------ | ------------------------------------------------------------------------------------------- |
| 무혐의 조기 종료(§4 `DISMISSED`)             | 2회    | 유효 기소 0건이면 변호·판사를 아예 실행하지 않는다(검사 1회만 소비)                         |
| 캐시 히트(§3 코드 해시 캐시)                 | 3회    | 이미 `SENTENCED`/`DISMISSED`된 동일 코드는 재판을 다시 열지 않는다(0회 소비)                |
| 진행 중 사건 차단(§3 부분 유니크 인덱스)     | 3회    | 판결 전인 동일 코드를 중복 제출해도 새 사건을 만들지 않아, 중복 제출이 쓸 뻔한 3회를 막는다 |
| 재심은 판사만 재실행(§4 `QUEUED_REJUDGMENT`) | 2회    | 검사·변호를 재사용하므로 전체 재실행(3회) 대신 판사 1회만 소비한다                          |

### 의도적으로 하지 않은 절약

판사에게 코드 전체 대신 증거 라인 주변만 발췌해서 주면 토큰이 줄어든다. 이 절약은 **의도적으로 채택하지 않았다** — 발췌본만 주면 변호인의 맥락 주장("이 호출은 진입점 근처라 예외를 통째로 잡아도 된다" 같은, 증거 라인 밖의 코드 구조를 근거로 드는 반박)을 판사가 검증할 방법이 없어진다. 토큰 비용보다 판결의 근거 검증 가능성을 우선해 전체 코드를 유지한다.

### 검증 지표

시스템이 설계 의도대로 동작하는지 운영 중 확인할 지표. 정상범위는 실제 데이터가 쌓이기 전의 초기 기준치다.

| 지표                   | 정의                                                                            | 정상범위 | 벗어났을 때 해석                                                                                                      |
| ---------------------- | ------------------------------------------------------------------------------- | -------- | --------------------------------------------------------------------------------------------------------------------- |
| 기소 폐기율            | 라인/법전 검증 실패로 폐기된 기소 수 / 검사 출력 전체 charge 수(폐기 전)        | 5% 미만  | 15% 초과 시 검사가 법전을 준수하지 않거나 라인 번호 계산을 잘못하고 있다는 신호                                       |
| 기각률                 | `verdict=DISMISSED`인 charge 수 / 재판이 진행된 사건의 전체 charge 수           | 10~30%   | 5% 미만이면 판사가 지나치게 강경, 40% 초과면 검사가 기소를 남발하거나 판사가 지나치게 관대함                          |
| severity 조정률        | `severity_adjusted=true`인 charge 수 / 살아남은 전체 charge 수                  | 10~25%   | 5% 미만이면 검사가 법전 기본값을 기계적으로만 사용, 50% 초과면 임의 조정 남발                                         |
| 항소 수용률            | `rebuttal_accepted=true`인 재심 성공 수 / 전체 재심 성공 수                     | 30~60%   | 90% 초과 시 판사가 사용자 주장에 과도하게 수긍한다는 신호(프롬프트 지침 강화 필요), 10% 미만이면 항소가 사실상 무의미 |
| `verdict_missing_rate` | verdict 누락으로 재시도된 판결 시도 수 / 전체 판결 시도 수                      | 5% 미만  | 높으면 기소 건수 상한(12건)만으로 부족하다는 신호 — 판례 주입량 축소나 상한 인하 검토                                 |
| `stale_commit_rate`    | 워커의 조건부 완료 커밋이 0행 적용되어 버려진 횟수 / 전체 스테이지 완료 시도 수 | 0%       | 0보다 크면 `locked_at` 15분 타임아웃이 여전히 짧다는 신호                                                             |

## 12. LLM 호출 설계

- **provider 추상화**: 검사/변호인/판사/재심 호출은 provider(예: Anthropic, OpenAI 등)에 직접 결합하지 않고 얇은 어댑터 뒤에 둔다. provider를 바꾸거나 장애 시 대체 provider로 전환할 때 워커 로직을 건드리지 않기 위함이다.
- **역할→모델 매핑은 설정값으로 관리**: "검사/변호인/판사/재심에 어떤 모델을 쓸지"를 코드에 하드코딩하지 않고 설정(환경변수/설정 파일)으로 둔다. §3에서 "단일 모델 + 역할별 프롬프트"로 결정했지만, 이후 특정 역할만 다른 모델로 바꾸는 실험을 코드 변경 없이 할 수 있어야 한다.
- **구조화 출력 강제**: 각 단계 호출은 자유 텍스트가 아니라 JSON 스키마를 강제하는 방식(예: provider의 구조화 출력/함수 호출 기능)으로 호출한다. §5의 스키마 검증은 이 구조화 출력이 실제로 스키마를 지켰는지 사후 검증하는 것이지, 자유 텍스트에서 JSON을 파싱해내는 것이 아니다.
- **`prompt_version` 기록**: 각 단계 호출에 사용된 프롬프트의 버전을 사건에 함께 기록한다. 프롬프트를 수정한 뒤 `verdict_missing_rate`나 기각률(§11) 같은 지표가 변하면, 그 변화가 어떤 프롬프트 버전 때부터인지 추적하기 위함이다.
- **429는 `stage_attempts`와 별도 카운터로 처리**: §4·§11에서 이미 정한 대로, provider의 rate limit 응답은 스테이지 총 시도 횟수(≤3)에 포함하지 않고 지수 백오프로 별도 재시도한다.
- **fixture 구현체**: provider 어댑터에 실제 LLM을 호출하는 구현체와, 미리 저장된 응답을 그대로 반환하는 fixture 구현체를 함께 둔다. 데모/시연 환경에서는 fixture 구현체로 전환해 LLM 비용 없이 정해진 샘플 코드에 대해 저장된 판결을 보여준다(§13 배포의 fixture 모드 참고). 재판 진행·검증·항소 흐름 자체는 fixture 모드에서도 실제 상태머신을 그대로 타므로, 시연이 실제 동작과 다르지 않다.

## 13. 배포

- FastAPI 앱과 워커를 같은 코드베이스에서 별도 프로세스로 기동(브로커 없이 PostgreSQL만 공유).
- **`RUN_WORKER_IN_APP` 폴백(기본값 false)**: 별도 워커 프로세스를 둘 수 없는 환경(예: 무료 플랜)을 위해 API 프로세스의 lifespan 안에서 워커 루프를 백그라운드 태스크로 대신 돌릴 수 있다 — 단 API 프로세스와 부하·장애가 뒤섞이고 워커가 죽어도 API가 감지하지 못하는 한계가 있어, 별도 프로세스가 가능하면 항상 그쪽을 쓴다.
- **실제 배포는 Render, 세 서비스 모두 Docker 기반**(`render.yaml` 참고) — 애초 계획한 "Vercel류 프론트엔드 호스팅"은 채택하지 않았다. 프론트엔드가 SSR(App Router, 서버 컴포넌트)을 쓰므로 정적 호스팅보다 Next.js standalone 빌드를 그대로 컨테이너로 돌리는 쪽이 백엔드와 배포 방식을 통일할 수 있어 더 단순했다.
  - `codecourt-api` — web, `server/Dockerfile`, 기동 전 `alembic upgrade head`
  - `codecourt-worker` — worker, 같은 이미지, `python -m app.worker_main`
  - `codecourt-client` — web, `client/Dockerfile`(Next.js standalone), `NEXT_PUBLIC_API_URL`을 빌드 시점 인자로 주입
  - PostgreSQL은 Render 관리형 인스턴스. AWS 등 직접 관리형 인프라는 여전히 쓰지 않는다 — 학교 과제 규모에서 서버·네트워크 구성을 직접 운영할 이유가 없다.
- 단일 PostgreSQL 인스턴스, 마이그레이션 도구로 스키마 관리(§8 ERD). **`cases(user_id, code_hash, language)`의 부분 유니크 인덱스(§3, 진행 중 사건 중복 생성 방지)는 이 마이그레이션에 포함되어야 한다** — 애플리케이션 배포와 별개로 잊기 쉬운 DB 제약이라 명시한다.
- `rules.yaml`은 배포 이미지/저장소에 포함되어 서버 부팅 시 로드된다. 조항 변경은 파일 수정 + 재배포로 이뤄진다(관리자 UI 없음, 비목표).
- 이메일 발송, 소셜 로그인, OAuth 서버 등 외부 인증 인프라는 필요 없다(비목표).
- 필요 환경변수: LLM API 키(fixture 모드에선 불필요), DB 접속 정보, JWT 서명 키, `CORS_ALLOWED_ORIGINS`, `ENVIRONMENT`. 전체 목록과 정확한 값은 `render.yaml`이 단일 출처다. GitHub 호출은 공개 API라 별도 자격증명이 필요 없다.
- 학교 과제 규모이므로 단일 리전·단일 인스턴스 배포로 충분하며, 오토스케일링·다중 리전은 비목표다.
- **fixture 모드 운영**: LLM API 비용을 확보하지 못한 상태이므로, 배포 환경은 fixture 모드로 운영한다(`LLM_PROVIDER=fixture`). 이 모드에서도 상태머신, 큐/워커 처리, 서버 측 스키마·라인·법전 검증, 판례 조회, 항소·재심 흐름은 모두 실제로 동작한다. 대체되는 것은 LLM 호출 지점 하나이며, §12의 provider 추상화를 통해 실제 키가 확보되면 설정 변경만으로 전환된다. 부수적으로 심사자가 매 시연마다 수십 초의 LLM 지연을 기다리지 않아도 되는 이점이 있다. `design.md` 6.8의 데모 모드 배너가 이 모드임을 화면에서 알린다.
- **데모 계정 제공**: `design.md` 5.1에 따라 로그인 화면 하단에 데모 계정 안내를 둔다 — 심사·평가자가 회원가입 없이 바로 둘러볼 수 있어야 한다. 계정 정보는 `README.md`(라이브 데모 절)를 단일 출처로 삼는다.
- 로컬 개발 환경은 `docker-compose.yml`(저장소 루트) 한 줄로 postgres/api/worker/client 전체를 띄운다 — 배포(`render.yaml`)와는 별개 구성이며 서로 대체하지 않는다. 자세한 사용법은 `README.md` "로컬 실행 방법" 참고.
