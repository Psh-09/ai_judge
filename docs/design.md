# Code Court — UI 디자인 브리프

> 화면을 그리기 위한 문서. 시스템 설계는 `plan.md`, API는 `openapi.yaml`을 본다.
> v0.2 — GitHub 링크 제출 방식 반영, 제품 내 안내(메뉴얼) 계층 추가

---

## 1. 제품 한 줄

코드를 제출하면 AI 세 역할(검사·변호인·판사)이 재판을 열어, **걸러진 지적**과 **실행 가능한 할 일 목록**을 주는 코드 리뷰 서비스.

사용자가 화면에서 느껴야 하는 것: "지적을 받았다"가 아니라 **"심사를 통과한 지적만 받았다"**.

---

## 2. 톤 & 무드

- **법정 문서.** 판결문 화면은 UI가 아니라 문서처럼 읽혀야 한다. 여백, 구분선, 좌측 정렬 본문.
- **다크 기반.** 코드가 화면의 절반을 차지하므로 코드 에디터와 이질감이 없어야 한다.
- **차분함.** 법정 은유를 쓰지만 장식적이면 안 된다. 망치·저울 일러스트, 양피지 텍스처, 세리프 장식체는 쓰지 않는다. 은유는 **용어와 구조**로만 표현한다.
- **판결은 무겁고, 형량은 가볍다.** 판결문은 정적이고 밀도 높게, 형량 체크리스트는 할 일 앱처럼 가볍고 조작 가능하게.

---

## 3. 디자인 원칙 5개

미적 취향이 아니라 제품의 작동 원리다. 어기면 제품이 성립하지 않는다.

1. **기각도 보인다.** 기각된 기소(`DISMISSED`)를 접거나 숨기지 않는다. 걸러진 과정이 보이는 것이 이 제품의 핵심 가치다.
2. **증거는 항상 라인과 함께.** 기소를 표시할 때 증거 라인 번호가 반드시 붙는다. 라인 없는 지적은 화면에 존재하지 않는다.
3. **심각도와 수정 비용은 다른 축.** severity와 effort를 같은 시각 언어(같은 색 계열, 같은 배지 모양)로 표현하면 안 된다. 사용자가 둘을 혼동하면 형량 체크리스트가 쓸모없어진다.
4. **진행은 상태로 보인다.** 재판은 수십 초 걸린다. 스피너 하나로 덮지 말고 어느 단계인지 보여준다.
5. **제품이 스스로 설명한다.** 별도 사용 설명서를 두지 않는다. 이 서비스는 IDE나 코드 호스팅 플랫폼에 통합되지 않은 독립 서비스여서, 사용자가 "무엇을 넣으면 무엇이 나오는지"를 화면 밖에서 배울 경로가 없다. 안내는 6장의 규칙에 따라 화면 안에 배치한다.

---

## 4. 디자인 토큰

값은 방향 제시이므로 조정 가능하다. 단 **의미 구분은 유지**해야 한다.

### severity — 심각도 (붉은 계열 단계)

| 값 | 의미 | 방향 |
|---|---|---|
| `HIGH` | 심각 | 채도 높은 레드 |
| `MEDIUM` | 보통 | 앰버 |
| `LOW` | 경미 | 뉴트럴 그레이 |

### verdict — 판정 (형태로 구분)

| 값 | 의미 | 방향 |
|---|---|---|
| `SUSTAINED` | 채택 | 실선 테두리, 강조 |
| `REDUCED` | 감형 | 실선 + 감형 화살표 표기 |
| `DISMISSED` | 기각 | 점선 테두리, 낮은 명도. 취소선은 쓰지 않는다 |

기각 카드를 흐리게 처리하되 **읽을 수 없을 정도로 낮추지 않는다.** 기각 사유는 반드시 읽혀야 한다.

### effort — 수정 비용 (severity와 다른 계열)

`SMALL` / `MEDIUM` / `LARGE` — 블루~틸 계열 또는 채워진 막대 1/2/3칸. **붉은 계열 금지.**

### 사건 상태 배지

`검사 중` / `변호 중` / `판결 중` / `판결 확정` / `무혐의` / `원심 확정(재심 실패)` / `재심 확정` / `실패`

### 타이포

- 본문: 시스템 산세리프
- 코드 · 라인 번호 · `rule_id` · 커밋 SHA: 고정폭
- 판결문 본문 행간 1.7 이상, 코드 블록 1.4

## 5. 화면 목록

### 5.1 로그인 / 회원가입

이메일 + 비밀번호. **"비밀번호 찾기" 링크를 두지 않는다** — 재설정 기능은 범위 밖이며, 동작하지 않는 링크는 없는 것보다 나쁘다.

로그인 화면 하단에 데모 계정 안내를 둔다(심사·평가자가 가입 없이 둘러볼 수 있어야 한다).

### 5.2 코드 제출 (접수 창구)

**입력 모드 2개를 탭으로 분리한다.** 두 모드는 상호배타적이다.

**모드 A — GitHub 링크 (기본)**
- URL 입력 필드 하나. 플레이스홀더에 형식 예시를 그대로 보여준다: `https://github.com/owner/repo/blob/main/src/app.py`
- 링크 입력 후 파일을 불러오면 **미리보기 카드**: 저장소 이름, 커밋 SHA(짧게), 파일 경로, 라인 수, 추론된 언어
- 미리보기 아래 코드 본문(읽기 전용, 라인 번호 표시)
- 커밋 SHA를 고정해 심사한다는 안내 한 줄: "이 커밋 시점의 파일로 심사합니다. 이후 저장소가 변경되어도 판결은 유지됩니다."

**모드 B — 직접 붙여넣기**
- 고정폭 textarea, 라인 번호, 라인/문자 카운터
- 로컬 코드나 아직 커밋하지 않은 코드를 심사할 때 쓴다는 안내

**두 모드 공통**
- 언어 선택: 링크 모드는 확장자 추론값을 프리필하고 변경 가능. `기타` 선택 시 안내 노출
- 자격증명 패턴 감지 시 경고 배너: "코드에 API 키로 보이는 문자열이 있습니다. 제출 전 제거를 권장합니다"
- 하단에 남은 제출 횟수
- 캐시 히트 모달 / 진행 중 사건 안내 (6.4 참조)

### 5.3 법정 (사건 진행)

3단 진행 인디케이터가 화면의 주역. 각 단계는 `대기 / 진행 중 / 완료 / 실패` 4상태.

```
[검사] ●완료  →  [변호인] ●완료  →  [판사] ◐진행 중
```

단계 완료 시 요약 한 줄이 누적된다. "기소 7건 접수 (2건 폐기)" / "변론 7건, 부인 5건" — 재판을 지켜보는 감각이 이 화면의 목적이다.

각 단계 아래에 그 단계가 무엇을 하는지 한 줄 설명을 상시 노출한다(6.3 참조). 대기 시간이 유일하게 사용자가 설명을 읽는 시간이다.

실패 시: 실패 단계 + 사유 + [다시 제출]. **완료된 단계의 산출물은 계속 열람 가능**해야 한다("기소장까지 보기").

### 5.4 판결문 ★ 가장 중요한 화면

위에서 아래로:

1. **상단 요약** — 사건 번호, 언어, 판결 상태 배지, 기소 N건 중 채택 N / 감형 N / 기각 N
2. **출처 블록** *(GitHub 링크 제출 사건만)* — `owner/repo` · 커밋 SHA · 파일 경로 · GitHub 원본 링크. 붙여넣기 제출 사건에는 이 블록이 없다
3. **제출 코드 블록** — 라인 번호 표시. 기소된 라인은 좌측에 마커
4. **판사 총평(`opinion`)** — 인용문 스타일, 문서체
5. **기소 카드 목록** — 각 카드:
   - `rule_id` + 조항명 (고정폭 + 일반체 조합)
   - 증거 라인 (`L42–L58`) — **클릭 시 상단 코드 블록의 해당 라인 하이라이트**
   - severity 변화: `HIGH → MEDIUM` (감형된 경우만 화살표 표기)
   - 판정 배지
   - 검사 주장 / 변론 / 판정 사유 3단 구조. 변론이 `NO_RESPONSE`면 "변론 없음" 명시
   - 참고된 판례가 있으면 "유사 판례 3건 참고" 표시
6. **형량 요약** — 과제 개수 + [형량 체크리스트로 이동]
7. **항소 버튼** — `appeal_used=false`일 때만 노출

무혐의(`DISMISSED` 사건)일 때는 판결문 대신 **무혐의 통지 화면**: "기소 가능한 위반이 발견되지 않았습니다" + 심사에 사용된 조항 수 + 코드 블록.

### 5.5 형량 체크리스트

- 항목별: 과제 문구, 대상 라인(`L42–L60`), effort 배지, 완료 체크박스
- `advisory=true` 항목은 "권고" 라벨 — 필수 아님을 구분
- 하단 고정: 이행률 바 (완료 / 전체). 체크 시 즉시 갱신
- 전체 완료 시 상태 표시. 축하 연출은 과하게 하지 않는다

### 5.6 항소 입력

모달. 반박 사유 textarea(20자 이상, 실시간 카운터).

**경고문 필수:** "항소는 사건당 1회만 가능하며, 접수 시점에 기회가 소진됩니다. 재심이 실패해도 다시 항소할 수 없습니다."

작성 가이드를 모달 안에 배치한다(6.5 참조).

### 5.7 재심 결과

- 성공: 판결문과 동일 레이아웃 + 상단 배너 "재심 확정". 원심과 판정이 달라진 기소는 변화를 표시 — `기각 → 채택` 등
- 실패: 원심 판결문 + 배너 "재심에 실패했습니다. 원심 판결이 유지됩니다" + 사유. **원심 내용이 사라진 것처럼 보이면 안 된다**

### 5.8 전과 기록

- 사건 목록: 사건 번호, 출처(저장소/파일 또는 "직접 제출"), 언어, 판결일, 상태 배지, 기소/채택 수, 이행률
- 반복 조항 랭킹: 자주 걸린 `rule_id` 상위 5개 + 횟수
- 빈 상태: "아직 판결받은 사건이 없습니다" + [코드 제출하기] + 첫 제출 가이드 링크

### 5.9 법전 열람 ← 메뉴얼의 본체

6.6에서 상세히 정의한다.

## 6. 제품 내 안내 계층 (메뉴얼)

이 서비스는 독립 웹 서비스이고 IDE·코드 호스팅 플랫폼에 통합되지 않는다. 사용자가 사용법을 배울 경로가 화면밖에 없으므로, **안내를 화면 안에 배치한다.** 별도 도움말 사이트나 PDF 매뉴얼을 만들지 않는다.

안내의 목적은 친절함이 아니라 **낭비 제거**다. 사용자가 잘못 제출하면 재판 한 건이 헛되고, 그건 처리 시간과 LLM 호출 비용을 그대로 태운다. 아래 각 안내는 특정 낭비를 막기 위해 존재한다.

### 6.1 배치 원칙

- **필요한 순간에, 필요한 자리에.** 시작 시 전체 설명을 몰아 보여주지 않는다
- **끄면 다시 뜨지 않는다.** 온보딩과 힌트는 dismiss 상태를 기억한다
- **모든 안내에는 행동이 붙는다.** "~할 수 없습니다"로 끝나지 않고 다음 행동을 준다
- 상시 진입점은 헤더에 **[법전]**과 **[사용 안내]** 두 개만

### 6.2 첫 진입 온보딩

3단 카드, dismiss 가능.

1. **무엇을 심사하나** — "GitHub 파일 링크 또는 붙여넣은 코드 한 파일을 심사합니다. 저장소 전체나 여러 파일은 심사하지 않습니다."
2. **어떻게 심사하나** — "검사가 기소하고, 변호인이 반박하고, 판사가 채택·감형·기각을 결정합니다. 기각된 지적도 이유와 함께 보여드립니다."
3. **무엇을 받나** — "판결문과 형량(할 일 목록)을 받습니다. 판결에 불복하면 1회 항소할 수 있습니다."

카드 하단: [법전 보기] — 무엇을 지적하는지 궁금한 사용자를 바로 조항 목록으로 보낸다.

### 6.3 진행 화면의 단계 설명

대기 시간에 노출되는 상시 텍스트. 각 단계 한 줄.

- 검사: "법전의 조항과 코드를 대조해 위반을 찾습니다. 조항에 없는 지적은 만들 수 없습니다."
- 변호인: "각 기소에 대해 반박합니다. 맥락상 과한 지적을 걸러내는 단계입니다."
- 판사: "기소와 변론을 함께 보고 채택·감형·기각을 결정하고, 할 일을 정합니다."

### 6.4 접수 화면의 낭비 방지 안내

| 안내 | 막는 낭비 |
|---|---|
| 라인/문자 카운터 + 툴팁 "심사 정확도와 처리 시간을 위해 한 번에 한 파일, 500줄까지 심사합니다. 긴 파일은 문제가 있다고 의심되는 부분만 잘라 제출하면 판결이 더 정확합니다" | 상한 초과로 반려되는 제출, 긴 파일로 인한 부정확한 판결 |
| 남은 제출 횟수 + 툴팁 "24시간 내 20건까지 심사합니다. 이미 판결받은 코드를 다시 열람하는 것과 링크를 불러오다 실패한 경우는 횟수에 포함되지 않습니다" | 횟수 소모를 걱정해 재시도를 못 하는 상황 |
| 캐시 히트 모달 "이미 판결된 코드입니다 (출처: `owner/repo@abc1234` · `path/to/file.py`). 같은 코드는 재판을 다시 열지 않습니다. 다시 재판하면 새 사건이 생성되고 제출 횟수가 소모됩니다." + [기존 판결 보기] / [다시 재판하기] | 같은 코드 중복 심사 |
| 진행 중 사건 안내 "이 코드는 현재 심사 중입니다" + [진행 상황 보기] | 동일 코드 동시 제출 |
| `기타` 언어 안내 "언어 종속 조항은 적용되지 않습니다. 공통 조항 N개만으로 심사합니다" | 지적이 적게 나온 이유를 오해하는 것 |
| 자격증명 감지 경고 | 비밀 정보가 판결문에 남는 것 |

### 6.5 항소 모달의 작성 가이드

항소는 1회뿐이고, 재심 실패 시 기회가 소진된다. 잘못 쓰면 그대로 날아가므로 가이드를 붙인다.

- 좋은 예: "이 함수는 단일 진입점 스크립트에서만 호출되므로 전역 변수 사용이 의도된 설계입니다"
- 나쁜 예: "이건 문제 아닙니다" / "다시 봐주세요"
- 한 줄 설명: "판사는 사용자 주장 자체를 근거로 인정하지 않습니다. 코드와 조항에 비추어 왜 적용이 과한지를 쓰면 반영될 가능성이 높습니다."

### 6.6 법전 열람 = 메뉴얼

이 화면이 사용 설명서를 대체한다. "이 서비스가 무엇을 보는지"를 조항 목록이 그대로 설명하기 때문이다.

구성:

1. **카테고리별 조항 목록** — `rule_id`, 조항명, 설명, 기본 severity, 기본 effort, 적용 언어. 비활성 조항은 기본 숨김 + 토글
2. **조항 선정 기준 요약** — 라인을 지목할 수 있고, 규약에 따라 갈리지 않고, 실행 없이 판정 가능한 것만 넣었다는 세 줄
3. **이 서비스가 보지 않는 것** ← 이 섹션이 특히 중요하다. 사용자가 기대할 수 없는 것을 미리 알려 헛된 제출을 막는다
   - 코드를 실행하지 않으므로 런타임 오류나 실측 성능 문제는 찾지 않는다
   - 파일 간 의존성, 아키텍처 수준의 설계 문제는 다루지 않는다
   - 포매터가 자동 처리하는 항목은 지적하지 않는다
   - 테스트 코드 작성 여부나 커버리지는 심사 대상이 아니다
4. **검색 필드** — 조항명·설명 텍스트 검색

### 6.7 에러 화면의 해결 행동

각 에러에 다음 행동을 하나 붙인다. 붙이지 않으면 사용자가 같은 요청을 반복해 자원을 태운다.

| 상황 | 문구 | 행동 |
|---|---|---|
| `INVALID_REPO_URL` | "GitHub 파일 링크 형식이 아닙니다. 저장소의 파일 페이지에서 주소를 복사해 주세요." | 형식 예시 표시 |
| `REPO_FILE_UNAVAILABLE` | "파일을 불러올 수 없습니다. 공개 저장소의 파일인지 확인해 주세요. 비공개 저장소는 지원하지 않습니다." | [직접 붙여넣기로 제출] |
| `FETCH_RATE_LIMITED` | "링크 불러오기 횟수를 초과했습니다. 잠시 후 다시 시도하거나 코드를 직접 붙여넣어 주세요." | [직접 붙여넣기로 제출] |
| 일일 제출 초과 | "24시간 내 20건을 모두 사용했습니다. 약 N시간 후 다시 시도할 수 있습니다." | 남은 시간 표시 |
| 코드 길이 초과 | "500줄 / 20,000자를 초과했습니다. 심사할 부분만 잘라 제출해 주세요." | 현재 값 표시 |
| `FAILED` | "심사에 실패했습니다. 완료된 단계까지는 확인할 수 있습니다." | [기소장 보기] / [다시 제출] |

### 6.8 데모 모드 배너

배포 환경이 fixture 모드로 운영되는 동안 상단에 얇은 배너를 상시 노출한다.

"데모 모드입니다. 준비된 샘플 코드에 대해 저장된 판결을 보여줍니다. 재판 진행, 검증, 항소 흐름은 실제로 동작합니다."

배너에 [샘플 코드 보기] — 데모에서 판결을 볼 수 있는 파일 목록으로 이동. 이게 없으면 사용자가 임의 코드를 넣고 왜 안 되는지 몰라 반복 시도한다.

## 8. 상태 및 엣지 화면

디자이너가 함께 받아야 하는 화면들. 빠지면 구현 단계에서 즉흥 처리된다.

- 로딩(사건 진행) / 빈 상태(전과 기록 없음)
- `FAILED` — 부분 결과 열람 포함
- 무혐의 통지
- 재심 실패 배너
- 6.7의 에러 6종
- 캐시 히트 모달 / 진행 중 사건 안내
- `기타` 언어 안내 / 자격증명 감지 경고
- 데모 모드 배너
- 링크 불러오는 중(로딩) / 링크 미리보기 완료

## 9. 마이크로카피 원칙

- **법정 은유는 라벨과 제목에만.** 기소, 변론, 판결, 형량, 항소, 법전, 전과 기록 — 여기까지
- **오류·안내는 평문.** "재판을 열 수 없습니다"보다 "심사에 실패했습니다. 다시 제출해 주세요"
- **판정 사유는 판사의 말투로.** "변론 인정. 스코프가 3줄이라 조항 적용이 과하다" — 서술체, 단정적
- **형량은 명령형 한 문장.** "42번 줄 쿼리를 파라미터 바인딩으로 교체"
- **안내문에는 이유를 붙인다.** "500줄까지 지원합니다"가 아니라 "심사 정확도와 처리 시간을 위해 500줄까지 심사합니다". 이유가 없으면 사용자는 제약을 우회하려 든다
- 사용자를 비난하지 않는다. 죄목은 코드에 붙는 것이고 사람에게 붙지 않는다

## 10. 화면 채울 더미 데이터

판결문 1건 전체. 디자이너는 이 데이터로 화면을 채운다. `Lorem ipsum`이나 "조항 1, 조항 2"는 쓰지 않는다.

**출처:** `octocat/sample-api` @ `a1b2c3d` · `src/handlers/user.py`
**사건:** 파이썬 187줄, 판결 확정, 기소 5건 → 채택 2 / 감형 1 / 기각 2

**총평:** "전반적으로 동작하는 코드이나, 입력 검증과 함수 단위 책임 분리가 미흡하다. 보안 관련 지적 1건은 즉시 수정이 필요하다."

| # | rule_id / 조항명 | 라인 | severity | 판정 | 판정 사유 |
|---|---|---|---|---|---|
| 0 | `SEC-003` SQL 문자열 결합 | L42 | HIGH | 채택 | "사용자 입력이 검증 없이 쿼리에 결합된다. 변론의 '내부 스크립트' 주장은 입력 경로가 외부에 열려 있어 성립하지 않는다" |
| 1 | `STRUCT-001` 함수 길이 과다 | L88–L140 | MEDIUM | 채택 | "52줄 단일 함수가 파싱·검증·저장을 함께 처리한다" |
| 2 | `ERR-002` 광범위 예외 처리 | L155–L158 | HIGH | 감형 (HIGH → MEDIUM) | "except 범위가 넓은 것은 사실이나, 로깅이 포함되어 실패가 은폐되지는 않는다" |
| 3 | `NAMING-002` 축약 변수명 | L17 | LOW | 기각 | "변론 인정. 스코프가 3줄이라 조항 적용이 과하다" |
| 4 | `STYLE-001` 매직 넘버 | L63 | LOW | 기각 | "상수의 의미가 인접 주석으로 설명되어 있어 가독성 저해가 없다" |

**형량:**

| 과제 | 대상 라인 | effort |
|---|---|---|
| 42번 줄 쿼리를 파라미터 바인딩으로 교체 | L42 | SMALL |
| `parse_and_save()`를 파싱·검증·저장 세 함수로 분리 | L88–L140 | LARGE |
| except 절을 예상 예외 타입으로 좁힘 | L155–L158 | MEDIUM |

이 데이터가 화면을 설명한다는 점을 유의: **HIGH인데 SMALL**(보안, 한 줄 수정)과 **MEDIUM인데 LARGE**(구조, 대규모 수정)가 동시에 있어서, severity와 effort가 왜 다른 축인지 화면만 봐도 드러난다. 더미 데이터를 바꿀 때 이 대비를 유지해야 한다.

## 11. 접근성 · 반응형

- **severity와 verdict를 색만으로 구분하지 않는다.** 텍스트 라벨 또는 형태를 반드시 병기
- 코드 블록 대비비 준수, 하이라이트는 배경색 + 좌측 마커 이중 표기
- 툴팁 내용은 키보드로도 접근 가능해야 한다. 안내가 마우스 호버에만 있으면 없는 것과 같다
- 데스크톱 우선. 코드를 제출하는 서비스이므로 모바일은 열람(판결문·형량 체크)까지만 지원
- 판결문은 인쇄/PDF 저장 시 레이아웃이 깨지지 않게 — 판결문을 저장해 두려는 사용자가 있다

## 12. 하지 말 것

- 기각 카드 접기·숨기기·탭 분리
- severity와 effort를 같은 색 계열로 표현
- 라인 번호 없는 기소 표시
- 망치·저울·가발 등 법정 클립아트, 양피지·나무 텍스처
- 재판 진행을 스피너 하나로 대체
- 판결 확정 전 형량 미리보기 (판사 판정 전에는 형량이 존재하지 않는다)
- 사용자를 나무라는 문구
- 별도 도움말 페이지·PDF 매뉴얼 (안내는 6장의 배치를 따른다)
- 첫 진입 시 전체 기능을 몰아 설명하는 투어
- 제약을 이유 없이 통보하는 문구
